VERDICT: BLOCKED

[B1] — The HTTP contract has no caller identity for any comment write. The standing `x-demo-token` check is a single shared secret and does not resolve a user, yet the proposed bodies omit `user_id` for post, vote, and report; optional viewer identity for shadow-own visibility is likewise not defined. `POST /notifications/read {ids}` also has no user with which to scope the update, so an implementation must either invent identity or update arbitrary notification ids.

FIX: In the stated dev-auth posture, put an explicit self-asserted `user_id` in all three comment commands and in mark-read (or make mark-read `/users/{id}/notifications/read`), and define an optional `viewer_id` that is honored only with a valid demo token. Scope every notification read/update by that user even though the shared token cannot prove the assertion. Make `subscribe_user` replace a socket's single user subscription, authenticate before mutating it or sending the snapshot, and document that real principal binding remains deferred.

[B2] — Hot-score arithmetic is safe in `i128`, but the list contract cannot provide its promised pagination stability. At the input maxima, `(i64::MAX / 3600 + 2)^2` is about `6.56e30`, well below `i128::MAX`, and the maximum result is only `536_870_912_000_000`; however, PostgreSQL `numeric / numeric` is fractional and a cast to `bigint` rounds rather than implementing Rust's positive integer truncation unless the SQL explicitly truncates. More importantly, a `(created_at, id)` cursor does not describe `ORDER BY hot_score`, and scores change as `now` crosses hour boundaries between pages, so rows can be skipped or repeated even if the formula itself matches.

FIX: Pin the SQL expression with `numeric` operands before the denominator square and explicit `trunc(... )::bigint`, deriving nonnegative whole `age_secs` with an explicit future-timestamp error path. Define total ordering and a hot cursor such as `(as_of, hot_score, created_at, id)`, reuse the cursor's `as_of` on every page, and order by all cursor fields. The Pg contract must compare exact Rust and SQL values—not merely ranks—at negative/zero scores, `i32::MAX`, 0/3599/3600 seconds, tie cases, and the maximum accepted age, plus assert the future-time failure.

[B3] — The notifier cursor protocol is missing the two facts that make it safe: migration 0006 never creates `outbox_cursors('notifier', 0)`, and the loop does not require `SELECT ... FOR UPDATE` on that cursor row. Concurrent pumps can therefore fail on first boot or process stale ranges and later regress `last_seq`. Copying the relay's `FOR UPDATE SKIP LOCKED` event query would be worse: while the relay holds a low-sequence event lock, the notifier could skip it, process a later row, advance its cursor past the skipped event, and lose its notifications permanently.

FIX: Seed the notifier cursor at zero in 0006; lock that one row before reading its value; fetch immutable outbox rows with a plain ordered `seq > last_seq` query and no row lock/`SKIP LOCKED`; bulk-insert; and set the cursor to the maximum fetched sequence in the same transaction. Test empty startup, rollback before insert, rollback after insert, partial-batch failure, two concurrent pumps, a stale-pump schedule, an unrecognized event that advances safely, and simultaneous relay row locks. Relay `published_at` updates and ordinary vacuum then do not interfere because the notifier reads retained MVCC rows by primary-key sequence.

[B4] — Exactly-once notification rows do not imply reliable or duplicate-free WS frames, because an in-process broadcast cannot be atomic with the database commit. Broadcasting before commit can expose phantom/duplicate frames on rollback; broadcasting after commit can lose live frames if the process dies between commit and send. The existing v1 protocol explicitly gives every outbox-derived frame an `outbox_seq`, but the proposed `notif` shape does not require `source_seq` or notification id, and the existing `WireEvent`/market-first filter is not a safe type for user-keyed traffic.

FIX: State the honest contract: rows are exactly-once, WS delivery is best-effort/at-least-once, and reconnect recovers via the authenticated unread snapshot plus REST list. Use a typed internal bus enum (market event versus committed user notification), filter the user variant before materializing a frame, and put `v: 1`, notification id, and `source_seq` on every `notif` frame so clients dedupe. Pick and test one broadcast boundary; if it is post-commit, add an injected commit-to-send crash test proving REST recovery rather than claiming lossless live delivery.

[B5] — The comment transaction does not serialize the spam rule. Two different idempotency keys from the same author can concurrently observe `recent_same_hash == 0` and both post visibly because `CommentTx` omits `UserLockGuard`; `body_hash` being author-scoped in the query does not close that race. Parent status/depth and `reply_count` can be made linearizable by locking the parent after the market, but the plan must also require vote/report insertion to win before changing the denormalized score/count; otherwise duplicate conflicts can drift counters, and “crosses threshold” is ambiguous after an admin restores a comment whose report count is already above threshold.

FIX: Add `UserLockGuard` to the post role and take the author lock after `serialize_key` and before `market_for_update`, then lock/revalidate the parent and bump its count in the same transaction as the child. Give vote/report deterministic guard keys, lock the comment, insert with the existing unique key first, and mutate score/report state only for an inserted row; emit the threshold event in that transaction. Define restore as either a durable curator override or a reset/new-threshold epoch, and test concurrent same-hash posts, duplicate votes/reports, parent moderation races, threshold races, and post-restore reports. Do not claim an existing global report velocity limit unless a comment-report limit is actually added.

[M1] — Migration 0006 corrupts denormalized thread metadata for existing data. `comments.parent_id` has existed since 0001, so `depth default 0` labels every preexisting reply as a root, while `reply_count default 0` ignores all preexisting children. The schema also still permits cross-market parents, arbitrary moderation strings, and negative depth/reply counts if an adapter errs.

FIX: Backfill depth with a cycle-detecting recursive CTE and direct reply counts with an aggregate before enforcing constraints; fail the migration on cycles or depth overflow. Backfill the chosen body hash consistently, add nonnegative checks and a moderation-status check, and enforce same-market parentage with a composite `(parent_id, market_id) -> comments(id, market_id)` foreign key after validating old rows. Contract-test a pre-0006 nested fixture through the migration.

[M2] — `NotifyReader` is named but its result cardinalities and event schemas are not sufficient to implement deterministic fanout. Phase 3 writes one settlement/void realization per positive holding/outcome, including zero-payout losers, while sell facts share the same table; a user can hold both outcomes, so “with a realization fact” can produce multiple `resolution_trade` candidates or wrongly include old sell-only facts unless the source and aggregation are pinned. `CommentPosted` lacks `author_id`, `MentionCreated` has no specified payload, and the `(user_id, source_seq)` index cannot itself collapse reply and mention because those are separate outbox events.

FIX: Define a consumed `OutboxEvent` carrying `seq` and versioned payload schemas. For resolution, use set-based reads that aggregate only the terminal `settlement`/`void` facts to exactly one row per user, anti-join voters against that set, and define the one-notification payload for a user holding both outcomes; define void participants as a distinct union of traders and voters. Include or query commenter id, parent author, mentioned user, and comment id so reply/self/mention suppression is deterministic. The partial unique key is then correct because policy guarantees at most one notification per `(event,user)`; add a real Pg test for a 1,000-participant event, a bulk insert, and a hard time bound (the Phase 3 `<2s` precedent is appropriate).

[M3] — The 0006 indexes do not cover the new bounded list and fanout shapes. `(market_id, created_at desc)` omits the UUID tie-breaker used by comment pagination; notifications have only an unread-count partial index but no `(user_id, id/created_at)` list index; `positions` has no outcome-first index for ranked holders; and the Phase 3 realization index starts with `created_at`, not the market/source keys used by resolution fanout or the user key used by profiles. These queries will sort or scan increasingly large tables despite small API limits.

FIX: Add indexes matching the final predicates and total orders, at minimum comments `(market_id, created_at desc, id desc)`, notifications `(user_id, id desc)`, positions `(outcome_id, cost_micro desc, user_id)`, and realizations paths for `(market_id, source, user_id)` and user history/summary. Pin deterministic tie-breakers for both holder columns and validate representative `EXPLAIN` plans plus the 1,000-recipient timing test; the dynamic hot expression itself remains a bounded sort unless a later materialized-rank design is justified.

[M4] — The moderation/mention contract is not deterministic as typed. Global rules say control characters are stripped, while `screen` says those same characters cause `Blocked`; “normalized body” for hashing is undefined even though storage is otherwise verbatim; byte, scalar, and grapheme length give different cap behavior; and `parse_mentions -> Vec<&str>` cannot case-normalize an uppercase handle without allocating a new string. `max_comment_len` and `spam_window_secs` also have no positive validation, so zero behavior is left to implementations.

FIX: Choose one control-character pipeline and one stored/hash input, specify Unicode length semantics and link parsing, and pin normalization with golden vectors. Return owned normalized handles (`Vec<String>` or equivalent), or explicitly accept only already-lowercase ASCII and remove the case-normalization claim. Require positive comment length and spam window, state that zero links/mentions deliberately disables those features if allowed, and cover malformed env values, Unicode, unmatched backticks, and normalization collisions.

CHECKPOINTS 1-8:

1. **Hot formula:** `i128` is sufficient; at score 0 or negative, ages 0/3599/3600 produce 250,000/250,000/111,111, and huge ages eventually truncate to zero. Exact-value plus ordering comparison is the right test strength, but the SQL truncation/future semantics and hot cursor/as-of contract must be pinned as in B2.
2. **Comment write path:** The safe order is guard → author lock (post only) → market lock → parent/comment row. A locked parent makes depth/status validation and reply-count mutation linearizable against moderation; unique vote/report insertion under the comment lock makes duplicates harmless. The present role omits the author lock, so concurrent hash spam is not safe, and restore/report semantics need the explicit rule in B5.
3. **Materializer exactly-once:** Before commit, any insert/cursor failure must roll back both; after commit, both are durable, so a restart sees the advanced cursor; a partial batch must not commit. That proof holds only with a seeded, row-locked cursor, max-sequence advancement, and no `SKIP LOCKED` on events (B3). Relay and notifier are independent under those rules; `published_at` and vacuum do not remove the retained event rows, though any future retention job must honor every consumer cursor.
4. **Fanout recipients:** Holder∧voter, self-reply, self-mention, and reply∧mention rules are product-consistent with §7.1 minus the named deferrals, but their set cardinalities are not yet implementable without M2's terminal-source aggregation and explicit event payloads. The per-user/source unique key is appropriate only after materialization guarantees one row per event/user.
5. **Privacy rule:** Suppressing vote side and score until a market is terminal is sound; Pg and fake contracts should define Paid as resolved-with-score and Voided as terminal-with-side but no score. No system comment/event payload should carry vote side; user-authored prose can voluntarily reveal it and cannot be prevented by this API. B1 must be fixed so shadow ownership does not become a caller-controlled leak.
6. **WS user channel:** A shared demo token is acceptable only as the explicitly temporary posture: anyone holding it can select another user, so it is not authentication. The blast radius is one selected user's notifications per socket only if subscription replacement, pre-snapshot token checking, and user-key filtering are explicit; the current plan does not yet impose that bound. Frames need the v1 sequence/dedupe treatment in B4.
7. **Holders by cost basis:** “By committed capital” is honest for Phase 4. The existing proportional cost relief means a partial sell reduces remaining cost and therefore rank without inventing mark-to-market value; use `cost desc, user_id` (or another pinned tie-breaker), exclude zero positions, make `limit` apply per YES/NO column, and keep the mark-to-market deferral visible.
8. **No-VCS / no-polling:** The plan contains no VCS operation. Holder refresh is event-triggered; a 2-second debounce/coalescing timer is not periodic polling, and notifications/comments/profiles specify no UI poll loop. The relay/notifier interval is infrastructure outbox consumption, not client polling, and should retain bounded batch/backoff behavior.
