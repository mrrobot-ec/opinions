B1. `crates/application/src/moderation_escalate.rs:125` — The leased runner claims and commits jobs, then only processes that returned batch; it has no transition that requeues or fails `running` jobs whose `lease_expires_at` has passed. Concrete failure scenario: a process claims 16 jobs and crashes after the claim transaction commits (or `process_job` returns a store error on the first job); every claimed row stays `running`, and every later tick only performs another ordinary claim, so those comments are never screened even after the leases expire and the `>= video_max_attempts` boundary is never applied. Suggested direction: add moderation expired-lease reclaim using the video-job semantics, including the same `>=` terminal boundary, cleared token/lease on requeue, pinned backoff, and fake/Pg crash-recovery coverage; because lines 132–134 process one shared-lease batch sequentially, also use bounded concurrency, nearer-to-call claims, or fenced renewal so the recovery path does not churn late batch members.

M1. `crates/adapters/src/llm/transport.rs:145` — The transport fully buffers `response.bytes()` before either adapter applies its advertised response cap (`crates/adapters/src/llm/draft.rs:157`, `crates/adapters/src/llm/moderation.rs:98`), so the caps do not bound memory or guarantee a typed overlength error. Concrete failure scenario: a malicious or malfunctioning configured endpoint returns a multi-gigabyte or fast unending chunked body; the process allocates until exhaustion (or buffers until the request timeout) before the 4 KiB/64 KiB checks can run, taking down the service instead of rejecting the response. Suggested direction: make the per-request response limit part of the transport contract and stream/read at most `limit + 1` bytes (also reject an oversized `Content-Length` early), with loopback tests for oversized success and non-200 bodies.

M2. `crates/adapters/src/llm/selection.rs:61` — Configuration validation rejects only blank API keys, not values that cannot be encoded as an HTTP bearer header, while the availability probe returns locally before the wire performs that validation (`crates/adapters/src/llm/moderation.rs:71`, `crates/adapters/src/llm/transport.rs:129`). Concrete failure scenario: `LLM_API_KEY='good\nbad'` plus a valid base URL selects the real preflight and passes startup with `Visible`; the runner then claims jobs, every real screen fails with `llm api key is not a valid header value`, and attempts back off and terminally fail instead of remaining queued with a typed startup configuration error. Suggested direction: validate the key's header representation during environment resolution without echoing the secret, poison both engines on failure, and add a runner-enabled startup/probe test proving zero claims for header-invalid keys.
