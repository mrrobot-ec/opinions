VERDICT: BLOCKED

[B1] — Task 3.0's EWMA contract is mathematically inconsistent. With the pinned `K_PPM = 965_936`, the specified floor-on-every-update recurrence gives `0 → 499_995` after twenty updates at `1_000_000`, and `1_000_000 → 499_988` after twenty updates at zero: the errors from an exact half-distance are 5 and 12 micro-units, not ±1. Repeated flooring also has a downward steady-state bias of up to roughly `1 / (1 - K/1_000_000)` (about 29 micro-units at H=20), while the plan neither defines an integer-only nth-root algorithm for arbitrary H nor rejects `k_ppm > 1_000_000` and rep/score values above `1_000_000`.

FIX: Specify either a bounded/precomputed set of half-lives or an integer root/rounding algorithm with tie behavior, constrain every fixed-point operand to `0..=1_000_000` and use checked `i128` intermediates, and replace the ±1 claim with exact recurrence vectors plus the proven accumulated-truncation bound. Validate H tightly enough that rounding cannot produce `K_PPM = 1_000_000`, which would freeze reputation.

[B2] — The proposed reputation write path is neither complete nor deadlock-safe. Migration 0001 defines `reputation`, but `PgTx::insert_user` only inserts `users`, so existing and future users have no row for `rep_for_update`; moreover, resolving two markets with overlapping voters can lock reputation rows in different vote-sequence orders, and a trade that correctly takes the existing user advisory lock before its market lock can deadlock against a resolver that takes the market first and user/reputation locks afterward. The per-voter `save_vote_score → rep_for_update → save_rep` interface also adds roughly three sequential round trips per voter to an already row-at-a-time settlement, which is not credible for the stated 1,000-voter case.

FIX: Add a 0005 reputation backfill and create the reputation row atomically in every user-creation path. Redesign the ports around bulk facts/reputation reads and bulk score/rep writes; acquire all affected user locks in canonical UUID order before `market_for_update` (using a stable preflight voter-id read for the already-Closed market), then perform set-based writes. Keep score, rep, tier-change outbox events, payout, and terminal state in the same transaction; the committed `resolve:<market>` guard then prevents replayed rep changes, and rollback leaves all of them retryable.

[B3] — The fee-discount authority and quote paths are underspecified and currently diverge. `PreviewTradeRequest` already carries `user_id`, and Converse supplies it, but `routes::preview_trade` discards it and `PreviewTradeCmd` has no user, so every HTTP/Converse preview still uses the pool's base fee. On execution, a plain `user_rep` read is unsafe: resolution of another market can lower the same user's tier concurrently because that other market's row lock provides no serialization for this market. Finally, quoting by replacing `Pool.fee` is observably inconsistent across adapters: Pg `save_reserves` ignores the fee, while the fake persists the whole returned `Pool`, accidentally converting a user-specific fee into the market fee.

FIX: Thread `user_id` through every preview caller and compute one shared `EffectiveFee` policy used by preview and execution. In execution, take the existing user lock before the market lock and read rep in that transaction; make the domain quote accept an explicit fee while preserving the pool's canonical fee in `pool_after`. Contract-test base and discounted buy/sell quotes across fake and Pg, and assert preview fee = trade row fee = ledger fees-account entry for both REST and Converse inputs.

[B4] — The sweep design does not enforce its central safety property. Current `ResolveMarket` accepts `Resolving`, rejects an override only when an override is present without a flag, and otherwise settles with `curator_override: None`; therefore (a) a second direct/admin resolve after the initial hold can settle before any report exists, and (b) a flagged market can settle without a curator decision. A passed market's payout cannot double-apply after a committed `resolve:<market>` ledger key, but the plan does not make the report verdict, `sweep:<market>` lifecycle command, state transition, and scheduler action one atomic/replay-defined protocol; merely catching a unique-report violation inside PostgreSQL would also leave that transaction aborted.

FIX: Make settlement from `Resolving` require one of exactly two locked authorities: a stored `pass` report with no curator flag, or an explicit curator decision when flagged; absence of a report must remain under review. Persist the `sweep:<market>` command and `Closed→Resolving` transition in the same transaction, insert the report with `ON CONFLICT DO NOTHING RETURNING` (then read the winner), and tighten `FlagCuratorNeeded` to an atomic `state='resolving' AND curator_flagged_at IS NULL` predicate. Tests must exercise direct/admin `None` both before a report and after a flag, concurrent report writers, pass retry after rollback, and two post-pass scheduler calls.

[B5] — Task 3.3's trader leaderboard is not realized PnL. A payout ledger entry is gross redemption, so a user with cost 1,000 and payout 1,200 would be reported as +1,200 instead of +200, while a losing position with zero payout has no positive user entry and its loss disappears. Sell realized deltas cannot be reconstructed from the specified trades/ledger join because `trades` stores no cost relieved or realized delta, and the settlement loop zeroes `positions.cost`; consequently the proposed SQL is both incorrect and unimplementable as written.

FIX: Persist immutable, timestamped realization facts transactionally for every sell and settlement (including zero-payout losses), keyed to the source trade/resolve transaction with a uniqueness constraint, and define leaderboard PnL as `SUM(realized_delta_micro)` in the half-open window. Count trades separately with an explicit window definition. Then sells are not double-counted: sold shares and relieved cost are absent from later settlement, while each realization fact contributes exactly once.

[M1] — The position-cap expression contradicts spec §3.3's “per market” rule. `positions` is keyed by `(user_id, outcome_id)`, so checking only `position.cost + gross` for the purchased side allows a user to hold the full cap in YES and another full cap in NO. Cost basis includes entry fees and is not mark-to-market exposure; that is defensible as a committed-capital limit, and exempting sells is safe because the existing proportional cost-relief formula cannot increase aggregate cost, but the product meaning must be stated honestly.

FIX: Under the already-locked market row, read/sum both outcome-position costs and enforce `sum(existing market costs) + buy gross <= tier cap`; keep sells exempt and add opposing-side/concurrent-boundary tests. Rename/document the metric as aggregate open cost basis per market (including fees), or choose and implement a different risk measure explicitly.

[M2] — `AdvanceDue` cannot perform the promised review flow as planned: its Pg/fake due queries exclude `Resolving`, `cascade` treats `Resolving` as terminal/no-op, and 0005 proposes no due index or review timestamp for that state. If `Resolving` is simply added with the old `closes_at`, the bounded loop can select a market again immediately after the hold and run the “2–5 minute” review in the same scheduler sweep; `ResolveReceipt`/`SweepReport` also have no held outcome with which to account for progress. The current curator helper only accepts `Closed`, while Phase 3 flags in `Resolving`.

FIX: Define a persisted `integrity_due_at` (or an explicit next-tick contract), set it during the hold, add a partial `(integrity_due_at, id)` index for unflagged `Resolving` markets, extend both due-query implementations and `cascade`, and add a distinct Held/UnderReview result. Keep the cascade from spin-selecting a newly held market, and allow only the sweep's locked `Resolving` path to win the curator flag.

[M3] — `VoteStats` cannot implement the checks promised by Task 3.0/3.2. Metadata coverage below half cannot be detected without observed subnet/device counts; `IntegritySweepConfig` has no device-concentration threshold or definition of the “young” account cutoff; and `prior_per_window_avg_ppm` has no defined prior horizon, denominator, zero-baseline behavior, or close-time anchor. A single aggregation also needs an explicit IPv6 policy because `/24` only describes IPv4.

FIX: Add `subnet_observed`, `device_observed`, a device threshold, and a young-account-age duration; define the final window relative to the locked `closes_at`, define the prior interval and integer scaling/zero-baseline semantics, and specify IPv4 `/24` plus an honest IPv6 prefix policy (or an explicit IPv6 skip). Persist counts, coverage, ratios, threshold/config version, and check strength in `integrity_reports.checks`, and pin SQL/domain boundary fixtures to the same definitions.

[M4] — Migration 0005's indexes do not support the planned read shapes. `(vote_scores.created_at)` helps voter ranking, but trader payout scans need a selective `ledger_transactions(kind, created_at, id)` path, sell/realization scans need a global time index, and daily fees filtered by account and time cannot use the existing `(account_id, id)` index efficiently. The “fees account” total also includes settlement dust, so presenting it as trade fees alone would be false.

FIX: After adopting immutable realization facts, index their `(created_at, user_id)` access path; add the payout transaction time index and an `(account_id, created_at)` ledger-entry index (with suitable included columns after `EXPLAIN` on representative volume). Define windows as UTC half-open intervals, and label the admin total as fees-account revenue with trade-fee versus settlement-dust breakdown, or persist those sources separately.

[M5] — The typed configuration contract is incomplete and has no fail-fast validation story. `RepConfig` as shown omits the advertised minimum fee, while its thresholds/caps/discounts can be unordered or out of range; the integrity config omits fields noted above; and the present main wiring silently substitutes defaults for malformed environment values. Applying `saturating_sub` plus a floor prevents a negative fee but can silently collapse several tiers to the same fee.

FIX: Give every config a validated constructor and make a present-but-invalid environment value fail startup. Require strictly ascending thresholds within `0..=1_000_000`, nonnegative/nondecreasing caps, valid half-life, ratio/multiplier ranges and nonzero windows, and discounts `<= 10_000`; add `min_fee_bps`, require each seeded base fee to be at least that floor, and either require each discount `<= base_fee - min_fee` or explicitly permit and test floor saturation. Test array parsing, boundary values, malformed lengths, and cross-config invariants.

[M6] — D23's kill-switch check is raceable if implemented through `MarketQueries` before `SeedMarket` opens its write transaction: two concurrent seeds can both observe PnL above the pause threshold and both commit, overshooting the circuit breaker. The sign convention for `pause_threshold_micro` is also unstated, and seed-time-only protection leaves already-live pools exposed indefinitely despite D23 describing an automatic pause on realized LP loss.

FIX: Evaluate the rolling PnL under a dedicated kill-switch advisory/config lock inside the seed transaction, with the explicit force override and its outbox audit in that same commit. Prefer a positive `max_loss_micro` and compare `sum <= -max_loss`, or validate/document the negative-threshold convention. Seed-time-only is acceptable for Phase 3 only as a stated bounded limitation with a follow-up for mid-market pause/exposure control.

[m1] — The sybil signals are weaker and more privacy-sensitive than their names imply. Default-off `TRUST_PROXY` correctly ignores spoofed XFF, but enabling it without validating that the peer belongs to a configured trusted-proxy CIDR lets a direct client forge the header; `/24` is only a rough IPv4 household/carrier proxy; and storing the sanitized `x-device-id` verbatim in a column named `device_hash` is not hashing and remains trivially reset/spoofed.

FIX: Honor forwarded addresses only from configured trusted proxy peers and define the selected-hop rule; HMAC the bounded device identifier with a server secret (or rename the column honestly). Record metadata coverage and labels such as `ip_prefix_proxy` and `client_asserted_device_id` with config/version in each report so the audit trail never presents either signal as attestation.

CHECKPOINTS 1-8:

1. EWMA integer math — Not sound as written: `K_PPM` rounds down from approximately 965,936.329 for H=20, repeated flooring has measurable downward drift, and the ±1 half-life assertion is false (B1). Inclusive-lower tier mapping is sound only after thresholds are validated.
2. Rep in the resolve transaction — Same-transaction and `resolve:<market>` replay semantics are sound after commit, but the row lifecycle, lock order, and N+1 port shape are blockers at 1,000 voters; canonical prelocking and batching are required now (B2).
3. Fee-discount coherence — Not coherent: REST discards the already-supplied preview user, Converse therefore receives base-fee previews, execution can read a stale higher tier, and an ephemeral fee on `Pool` makes fake/Pg persistence differ (B3). One explicit effective-fee input must drive quote, receipt, trade row, and ledger.
4. Sweep semantics — The hold threshold must use escrow read after authority is established under the locked market/state, but current proposed control flow has two flagged-pot bypasses: direct resolve before a report and resolve-with-`None` after a flag (B4). A committed pass cannot double-pay because of `resolve:<market>`, yet report/lifecycle/action idempotency and `Resolving` scheduling still require the atomic protocol and due-time design in B4/M2.
5. Sybil-signal honesty — `TRUST_PROXY=0` is the correct safe default; `/24` and a localStorage identifier are deliberately weak signals, not identity proofs. They are acceptable only with trusted-peer XFF handling, IPv6/coverage rules, server-side pseudonymization, and explicit weak-signal labels in every audit record (M3/m1).
6. Trader-leaderboard SQL — Unsound: gross payouts are not PnL and sell deltas are absent from the schema, so the proposed query cannot be made correct or O(window) with the listed indexes (B5/M4). Immutable realization facts remove ambiguity and do not double-count sold shares.
7. Kill-switch placement — A seed-time-only check is an acceptable Phase 3 scope if the ongoing exposure of live markets is explicitly documented, but a pre-transaction read is raceable and not a reliable circuit breaker (M6). Move it into the locked seed transaction and state the deferred mid-market control.
8. No-VCS/polling discipline — Confirmed: the Phase 3 plan requires no VCS command, artifact reproducibility uses generation plus `cmp`, and one REST fetch on page load is not polling because no timer/interval is introduced.
