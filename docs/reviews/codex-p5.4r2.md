## New findings

M1. `crates/application/src/moderation_escalate.rs:183` — The user-visible escalation commits before, and in a different transaction from, the token-fenced completion at `:227`; therefore the fence drops only the stale job-row completion, not the stale moderation result. Concrete failure scenario: runner A claims a Visible comment and receives `Shadow` after its lease expires; runner B reclaims the job and either completes a newer Visible attempt or terminally fails it, clearing/replacing A's token; A then locks the still-Visible comment, commits Visible→Shadow, and only afterward has its old-token completion rejected. The durable job says the newer attempt won (or no further attempt was allowed), yet A's stale result still changed the comment, and the existing stale-token test exercises `complete` directly rather than this side effect. Suggested direction: make token ownership validation, severity recheck/comment update, and moderation-job completion one atomic store operation/transaction; a separate precheck would retain the race.

M2. `crates/application/src/moderation_escalate.rs:43` — Stage 2 still claims 16 rows with one common `now + lease` and then screens them sequentially at `:147`, while the real request timeout is 30 seconds (`crates/adapters/src/llm/selection.rs:29`) and the default lease is 60 seconds (`crates/application/src/model.rs:583`). Concrete failure scenario: with 16 due comments and a healthy endpoint taking 25 seconds per response, runner A cannot begin job 4 before the entire batch's leases expire; runner B reclaims and reclaims the tail, causing duplicate outbound calls and attempts, and repeated runners can reach `video_max_attempts` and terminally fail later jobs before their original owner reaches them. Suggested direction: claim nearer to each call, process a safely bounded concurrent batch, renew leases with fencing, or size the claim unit/lease from a defensible worst-case duration; add a two-runner slow-preflight test that proves live work is not reclaimed.

M3. `crates/application/src/moderation_escalate.rs:198` — `process_job` converts every `StoreError` from comment read/screen/apply into an ordinary retry/terminal completion, so permanent `Invariant` and `Integrity` failures disappear from the tick whenever the completion transaction succeeds. Concrete failure scenario: a corrupt comment row makes the comment adapter return `StoreError::Invariant`; the runner writes that text to the job, returns `Ok(())`, repeats until `video_max_attempts`, and leaves the job Failed while every tick reports success, masking a systemic store/schema fault from the runner supervisor. Suggested direction: still fence/settle the affected job and continue the batch, but classify non-retryable store errors and return the first fatal one after the tail; reserve attempt-only handling for expected remote/transient per-job failures.

m1. `crates/application/src/contract/video.rs:783` — The new moderation reclaim contract claims to pin lease-expiry ordering and terminal error coalescing, but it gives both rows the same expiry, never observes which row the limit-1 call reclaimed, and cannot inspect an error because `ModerationJobRow` has no error field (`crates/application/src/model.rs:464`); the fake likewise stores no moderation error while Pg does at `crates/adapters/src/pg/video_tx.rs:597`. Concrete failure scenario: fake or Pg reclaim is changed to newest-expiry-first and Pg stops writing `"lease expired"`; both contract suites still pass because they assert only counts/eventual statuses and both equal-expiry rows are ultimately reclaimed. Suggested direction: create distinct expiry times, assert the exact first reclaimed identity/state after limit 1, and expose a contract-only/read projection of moderation error so fake and Pg must share preserve/coalesce semantics.

m2. `crates/adapters/src/llm/transport.rs:414` — The cap tests cover far-over declared and streamed bodies but do not pin the contract boundary that exactly `max_response_bytes` must pass and `cap + 1` must fail. Concrete failure scenario: a maintenance edit changes either `>` at `:150`/`:163` to `>=`; the suite remains green, but a valid response exactly 4,096 or 65,536 bytes is rejected. Suggested direction: add exact-cap success and cap-plus-one failure cases for both declared-length and undeclared/chunked reads.

N1. `crates/adapters/src/llm/selection.rs:223` — The test helper restores environment variables only after `body()` returns normally, despite the resolution describing the helper as poison-safe. Concrete failure scenario: an assertion inside a `with_env` body panics; unwinding skips lines 238–243, leaves temporary LLM credentials/base URL installed process-wide, and later tests deliberately recover the poisoned mutex and run against the leaked override. Suggested direction: use an RAII restoration guard whose `Drop` restores both saved `OsString` values, and test restoration through `catch_unwind`.
