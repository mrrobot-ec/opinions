BLOCKED

1. **[BLOCKER] Plan §1 D24 (Config store), also §4.3–4.4 (hot propagation and kill-switch proofs): the cursor is not ordered by transaction commit.**

   **Failure scenario:** PostgreSQL assigns `events_outbox.seq` when a row is inserted, not when its transaction commits. Config transaction A can write `trading_paused=true` and obtain sequence 100, then stall before commit; unrelated config transaction B can obtain sequence 101 and commit first. The dedicated consumer, even while correctly holding its one cursor row lock, can see 101 but not A's uncommitted 100, fold B, and advance `last_seq` to 101. When A commits, `seq > 101` will never return the pause event, so the in-process snapshot can remain unpaused until restart. Reusing the notifier's plain ordered cursor pattern prevents competing consumers, but it does not make identity order equal commit order.

   **Concrete fix:** Do not use outbox sequence as the authoritative config watermark. Add one globally serialized config generation (a singleton row locked by every config write), validate and commit a complete snapshot/patch at generation N, and have the consumer reconcile directly from `config_entries` whenever the authoritative generation exceeds its applied generation; the outbox event should only wake the reconciler. Alternatively, consume a dedicated config change log ordered by that serialized generation, not `events_outbox.seq`. Add a two-connection Pg contract test that commits N+1 while N is open and proves N is eventually applied rather than skipped.

2. **[BLOCKER] Plan §1 D25 (Kill switches): a watch-snapshot check is not a guarded-corridor safety barrier, and `PreviewTrade` has no `serialize_key` corridor.**

   **Failure scenario:** `PlaceTrade` can acquire its idempotency guard, read `trading_paused=false` from the watch receiver, block on a user/market/account lock, and then commit after the admin pause transaction has committed and even after the watch has changed to `true`. A new request can likewise read the old snapshot during the stated sub-two-second propagation window and commit after the pause. The operator therefore cannot know that a successful pause response fences later commits. Separately, the existing `PreviewTrade` is intentionally a lock-free `MarketQueries` read with no write transaction or idempotency key, so the instruction to check it "after `serialize_key`" is unimplementable.

   **Concrete fix:** Define an explicit linearization point. Each trade/vote transaction should acquire shared global and market pause fences in a pinned position in the global lock order, read the authoritative pause rows under those fences, and hold them through commit; a pause mutation should acquire the matching exclusive fence before changing the row and return only after commit. Then every pre-pause writer finishes before the pause returns and every later writer sees the pause. Keep preview rejection explicitly best-effort via the watch snapshot, with `PlaceTrade`/`CastVote` as the final authority. Add races for pause versus a writer stalled before the market lock, before ledger apply, and before commit, plus global/per-market fence ordering tests.

3. **[MAJOR] Plan §1 D24 and §0 Ops control-plane scope: per-key versions and write-time validation do not define an atomic, valid `ConfigSnapshot`, and the exit proof covers only one tunable.**

   **Failure scenario:** Interdependent settings can be updated one key at a time and observed in mixed generations. For example, a new threshold/floor can be applied before its corresponding limit, or a hidden-window value can be combined with an old open duration, even though neither individual JSON value is malformed. Existing use cases and workers currently receive typed configs by value, while existing market deadlines and pool fees are persisted; the plan does not say which of the spec's fee, seed, reputation, integrity, cadence, payout, and feature settings affect existing entities, newly created entities, or long-lived loops. The smoke test's `trade_fee_bps` preview cannot prove the promised "everything tunable" propagation.

   **Concrete fix:** Make `SetConfig` an atomic typed patch over the whole prospective snapshot, validate cross-key constraints, assign one global generation, and publish/replace only complete snapshots. Inventory every §10.2 key with type, bounds, RBAC capability, consumer, and effective-time semantics (for example, seed size applies to new markets; persisted deadlines do not move unless an explicit reschedule action does). Add propagation tests for every consumer class and a batch update that would be invalid or transiently invalid if applied key-by-key.

4. **[BLOCKER] Plan §1 D26 (RBAC + audit), §2 deliverables, and §3 W1/W2: the proposed `OpsTx` cannot atomically audit the repository's existing admin mutations.**

   **Failure scenario:** Existing advance, resolve/void, comment moderation, and draft create/edit/approve/reject/publish handlers invoke application use cases that open and commit `AdvanceTx`, `ResolveTx`, `CommentTx`, or `ContentTx`. If a route then opens `OpsTx` to add `admin_actions`, a crash or database failure between those commits leaves an admin effect with no audit row. Taking `before` in the route also races the effect's row locks. The same issue applies if replay/refanout performs work first and audits afterward; external notification delivery can never be in the database transaction.

   **Concrete fix:** In Task 6.0, introduce an `AdminContext` plus `AuditWriter` in the final transaction role of every current and new admin mutation, not only the new ops endpoints. Capture before/after under the same locked transaction and insert the audit row before its one commit. Define replay/refanout's atomic effect as enqueueing a durable, idempotent command/job together with the audit row; a leased runner performs delivery later. Run fake and Pg contracts over every admin mutation with injected failures before effect, between effect and audit, at audit insert, and at commit, proving all-or-nothing behavior.

5. **[BLOCKER] Plan §1 D26, §0 stand-ins, and §4.7 (RBAC): the RBAC boundary is incomplete and retains obvious bypass paths unless all legacy admin routes are migrated.**

   **Failure scenario:** "route table declares required role" supplies no exhaustive capability matrix, and labels such as `ops+` are ambiguous because curator, ops, and finance are sibling responsibilities rather than a total order. The current repository has route-local `ADMIN_TOKEN` checks (including a development fallback) across core, social, and content routers. Adding RBAC only in `routes/ops.rs` leaves those mutations reachable with the legacy token and outside the new audit contract. "Audit reads are admin-only" can also expose finance/superadmin actions and token fingerprints to every curator. The staging faucet can mint arbitrary balances if it is accidentally enabled with the production binary.

   **Concrete fix:** Enumerate every `/admin/**` route, including existing advance/resolve/moderation/content/fee reads and the new faucet/config/audit/manual-ops routes, in a capability matrix with no implicit hierarchy. Enforce it in one fail-closed middleware/layer before routing, remove the legacy token and fallback, use constant-time comparison against high-entropy token digests, reject empty/duplicate/malformed role maps at startup, redact stored token hashes from ordinary audit responses, and restrict audit reads to an explicit capability. Require an explicit non-production mode as well as finance/superadmin capability for the faucet, with startup tests proving it cannot be mounted in production.

6. **[BLOCKER] Plan §1 D30 (Unwind), also §4.7: the eligible states and promised balance restoration are incompatible with the existing settlement lifecycle and non-negativity rule.**

   **Failure scenario:** A normal resolution currently walks `Resolving -> Resolved -> Paid` in one transaction, so no normal market is durably left in the plan's allowed `Resolved` state; the exit criterion only exercises `Voided` and hides this. Both paid and voided settlement have already credited payouts, zeroed position shares/cost, and written terminal realizations. A winner can then withdraw or spend the payout. Debiting that user's payout during unwind makes the internal user account negative and is rejected by D13's ledger rule, so append-only reversals do not restore pre-market balances "by construction."

   **Concrete fix:** Choose and document one feasible product rule before build. Either introduce a durable pre-payout state/reservation and allow full unwind only before redemption, or redefine post-payout unwind as a house-funded remedial refund that never claws back settled funds and stop claiming pre-market restoration. If post-payout clawback is retained, it must lock every affected user/account canonically, prove sufficient reserved balance, and return a typed refusal otherwise. Add normal-paid, voided, payout-spent, withdrawal-settled, and concurrent-spend cases to the Pg contracts and E2E.

7. **[BLOCKER] Plan §1 D30 (Unwind): "idempotent by unwind key" does not prevent a second unwind or define exactly-once reversal lineage and derived-state repair.**

   **Failure scenario:** Two callers can submit different keys for the same market and both apply reversals. A settlement transaction is referenced by many realization rows, so an implementation iterating realizations can reverse the same payout transaction multiple times. Conversely, reversing only each trade's user leg and payout leg leaves fee/dust, escrow, pool payout, LP PnL, outcome redemption, `realized_pnl`, realizations, notifications, and the market's terminal state inconsistent. The global ledger key namespace also permits an unprefixed caller key to collide with a trade/deposit key.

   **Concrete fix:** Add a durable `market_unwinds` authority with `market_id` unique/primary and a deterministic namespaced key, plus database-enforced reversal lineage (`reversed_txn_id` or `reversed_entry_id` unique). Select a distinct, precisely enumerated set of original ledger transactions/entries once, lock the market and affected accounts canonically, and commit reversals, unwind marker/state, audit, and outbox atomically (or specify a fenced staged saga if one transaction is too large). Define treatment of seed, trade fees, payout dust, pool payout, positions, realizations, LP PnL, and projections. Test two different request keys concurrently, N realizations sharing one payout transaction, crash/retry, and projection queries after unwind.

8. **[BLOCKER] Plan §1 D27 (Invariants): the stated conservation equation is not the ledger's actual identity and several terms are not micro-exact from the named tables.**

   **Failure scenario:** The ledger has user, pool, fees, house, escrow, and external accounts in two currencies. `deposits - withdrawals = user balances + pool value + fee accounts` omits house and escrow, ignores the external contra account and `usdc_credit`, and never defines which payment statuses count. Pool reserves are outcome shares, not a micro-USDC balance with an exact mark-to-market value. Terminal user realizations omit the pool's payout and fee-account dust, so they cannot alone prove payouts equal close collateral. The proposed sweep can therefore pass while omitting collateral or report drift on a valid seeded/live/settled market.

   **Concrete fix:** Pin separate exact identities per currency: every ledger transaction sums to zero; all non-external accounts are nonnegative; `-external_balance = sum(all internal account classes)`; credited/settled payment facts reconcile to their linked external ledger entries; and each market's escrow/complete-set history reconciles seed, trades, payout, fees, and reversals. For resolution, record collateral-at-close or derive a formally specified pre-payout escrow value, and require payout positive legs (users + pool + dust-to-fees) to equal the escrow debit. Add seed-only, live-trading, fee, dust, credit-currency, deposit/withdraw, void, and unwind fixtures against both fake and Pg.

9. **[MAJOR] Plan §1 D27 and §0 continuous sweep: `InvariantQueries` does not promise one consistent database snapshot.**

   **Failure scenario:** If the use case calls several pool-backed query methods under PostgreSQL's default `READ COMMITTED`, each statement can see a different set of committed trades/deposits/resolutions. A trade committing between the external-balance query and the internal-account query can create a false drift, while related checks may describe mutually impossible states. Pausing swarm actions between cycles does not stop lifecycle workers, and the proposed continuous production loop necessarily races writers.

   **Concrete fix:** Replace the loose query port with an `InvariantReadTx`/snapshot role whose Pg implementation begins one `REPEATABLE READ, READ ONLY` transaction (or execute the entire report in one statement/snapshot) and whose fake clones one immutable state at begin. Return a snapshot identifier/as-of with the report, impose a statement timeout, and avoid writer locks. Add a concurrency contract that commits a trade during a blocked sweep and proves the report corresponds wholly to either the before or after state, never a mixture.

10. **[BLOCKER] Plan §1 D28 (simswarm architecture) and §4.2 (replay determinism): identical seeds cannot produce identical live action logs under the proposed inputs and scheduler.**

   **Failure scenario:** A decision is pure only after its `market_view` is fixed, but that view is fed by live HTTP/WS state changed by 2,000 racing agents. Tokio task scheduling, request completion order, server-generated IDs/timestamps, WS delivery/reconnect order, timeouts, and HTTP retry outcomes change that input between runs. Per-agent ChaCha streams prevent RNG sharing but do not control those sources. The second run is suddenly described as `dry-run` even though no dry-run CLI/trace contract is specified, and running it after the first run observes a mutated database. Raw latency/completion logs also necessarily differ.

   **Concrete fix:** Narrow the seed claim to a deterministic planned-intent schedule, or add trace replay. Precompute a total order such as `(sim_tick, agent_index, local_seq)`, derive stable logical IDs/idempotency keys from the seed, and keep wall-clock latency/completion data in a separate non-compared log. Buffer WS inputs to tick boundaries, dedupe/order by `outbox_seq`, define gap/snapshot recovery, and make retries deterministic in sim time. For executed-decision replay, record every market-view input and HTTP/WS outcome and replay that trace; for two live-run comparison, reset to identical scenario manifests/databases and compare a normalized intent log with an explicitly stated concurrency policy. Add the missing dry-run/trace CLI contract to D28.

11. **[MAJOR] Plan §1 D29 and §4.5 (resolver kill): the claimed mid-payout chaos drill is probabilistic and does not hit an observable crash seam.**

   **Failure scenario:** Current resolution and payout are one short database transaction, not a leased payout job with a durable mid-stage. A black-box controller that sees a market enter Closing and sends `SIGKILL` cannot know whether it killed before resolution began, during the transaction, or after commit; most green runs can exercise only process restart while still claiming exactly-once recovery "under fire." The plan explicitly says process kill needs no product seam, so there is no deterministic proof that the ledger write-before-commit window was reached.

   **Concrete fix:** Add an explicitly staging-only, armed crash barrier/fault port at a named point after payout ledger work and before commit; the harness must arm it, wait for an observable readiness acknowledgement, kill the process, restart, and prove rollback/replay/one payout. Protect that barrier with the same two-factor non-production chaos enablement as other faults. If no deterministic seam is acceptable in product code, downgrade the exit criterion to random process kill/restart and stop calling it a mid-payout idempotency proof.

12. **[MAJOR] Plan §1 D29 (Chaos fault seams): `Noop` by default is insufficient production containment, and the two implementations' test contract is underspecified.**

   **Failure scenario:** A leaked or mistakenly set `CHAOS_RELAY_DELAY_MS`/`CHAOS_WS_DROP_EVERY_N` activates fault behavior in the production adapter binary and can violate SLOs or disconnect users. A global "every N" counter is itself scheduling-dependent across connections, so the same chaos seed need not drop the same frame. Merely line-covering `Noop` and fault implementations does not prove startup selects `Noop`, that malformed/partial config fails safely, or that the no-fault path is observationally transparent.

   **Concrete fix:** Require both an immutable non-production environment and an explicit `CHAOS_ENABLED` arm; reject any chaos knob at startup in production and reject partial/malformed values rather than silently enabling/disabling. Parse once into typed config, expose the active fault mode in health/metrics, inject sleeper/counter/connection scope, and make WS drops deterministic per connection/run. Define separate contracts for Noop transparency and each injected fault, plus startup-composition tests and an E2E assertion that the ordinary profile has zero injected faults.

13. **[BLOCKER] Plan §3 (4-way wave + barrier): the wave is neither file-disjoint nor pre-frozen as compiling final contracts.**

   **Failure scenario:** W1 and W2 both require the single `pg/ops_tx.rs`, `http/routes/ops.rs`, and `http/dto/ops.rs` named in §2. D28 assigns `simswarm/src/chaos.rs` to W3 while W4 also owns the chaos controller. `main.rs`, route modules, port modules, workspace files, and migration are frozen, but Task 6.0 does not pre-wire the config receiver/consumer, RBAC layer, invariant loop, fault composition, final Store factories, DTO/OpenAPI registrations, or fake/Pg placeholders that the wave needs. "Extend shared traits only with defaulted methods" permits required behavior to silently fall through and is weaker than Phase 5's behavior-tested unavailable placeholders. Coordinator-mediated edits during the live wave invalidate other workers' compilation assumptions and the manifest.

   **Concrete fix:** Give Task 6.0 an exhaustive ownership matrix and final, compiling contracts for all cross-wave types. Pre-write and behavior-test Store factories, fake/Pg placeholders, AppState/main composition, route/RBAC middleware registration, DTO/OpenAPI surfaces, errors/models/events, simswarm client/chaos boundaries, migration, gate scripts, and manifest tooling; required trait methods must not have permissive defaults. Assign W1/W2 separate route/DTO/Pg modules and one owner for chaos. Any frozen change must stop the wave, be integrated and re-manifested by the coordinator, pass the skeleton gates, and only then release workers again.

14. **[BLOCKER] Plan opening engineering bar, §2 simswarm inventory, and §3 Task 6.0/barrier: the new crate fails the repository's current dependency/HTTP gates before tests run.**

   **Failure scenario:** `scripts/check_dependency_rule.py` rejects every workspace crate not present in its `ALLOWED` map, so adding `simswarm` immediately produces `unknown internal crate simswarm`. The current `just deps-check` also rejects any `reqwest::Client` construction outside `crates/adapters/src/llm/transport.rs`, directly conflicting with D28's real `simswarm::HttpClient`. Neither gate script is assigned to Task 6.0's frozen surface. If simswarm imports adapter DTOs to avoid duplication, it also ceases to be a public-API-only external harness. The 100% library gate is not credible unless OS process control, sleeping/retry, HTTP, and WS creation are injectable and covered; current coverage recipes do not include the new package.

   **Concrete fix:** Task 6.0 must own, update, test, and freeze both dependency/gate scripts and all simswarm dependencies before the wave. Model simswarm explicitly as an outer test harness with no internal crate dependency (use generated/public wire models), allow HTTP construction only in one audited simswarm transport module while retaining the LLM confinement, and add a gate-test that catches construction elsewhere. Add a fourth explicit `cargo llvm-cov -p simswarm --fail-under-lines 100` recipe, keep the binary thin, and put process/spawn/sleep/HTTP/WS behind injected roles so fake and local-stub contracts can cover every library line without external network access.
