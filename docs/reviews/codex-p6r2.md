## Round-1 finding verification

1. **PARTIAL — config outbox ordering.** D24's authoritative `config_generation` plus full-snapshot reload and periodic reconciliation fixes the lost-outbox-event failure: outbox sequence is now only a wake-up. However, the required Pg test is impossible as written: if every config writer first locks the singleton row, transaction B cannot obtain generation N+1 and commit while transaction A at N is held open. The contract must instead prove B blocks behind A, then separately prove a missed wake-up is healed from the authoritative generation.

2. **PARTIAL — kill-switch linearization.** D25 replaces the watch read with shared/exclusive transaction fences and correctly leaves preview best-effort. The chosen position and scope are not operationally sound, though: every queued trade and vote takes both shared fences before the existing user/market bottlenecks and retains them through commit, so an exclusive pause can sit behind the whole queued convoy; votes also delay a trading-only pause. NEW-1 gives the blocking scenario.

3. **PARTIAL — atomic config snapshots and complete catalog.** Whole-snapshot patching, cross-key validation, one generation, and apply-to classes resolve mixed snapshots in principle. The plan itself still does not enumerate every §10.2 key or its consumer: reputation thresholds, vote-velocity/integrity settings, cadence/schedule, and several feature consumers are only covered by the claim that migration/copy will enumerate them, while withdrawal settings are expressly deferred. D25a also contradicts the fee effective-time rule; see NEW-8.

4. **UNRESOLVED — atomic audit of existing admin mutations.** Adding `AuditWrite` to a transaction role does not make existing use cases call it with an authenticated actor or capture before/after under their locks. More decisively, `/admin/drafts/{id}/publish_now` runs `PublishDraft`, which commits multiple `ContentTx`, seed-ledger, and advance transactions; no one insertion in a "final transaction role" can be atomic with that admin effect. Task 6.0 does not assign the existing use-case call sites or their test doubles. See NEW-2.

5. **PARTIAL — RBAC and faucet containment.** The explicit capability sets, single fail-closed layer, removal of `ADMIN_TOKEN`, startup token-map validation, constant-time digest comparison, and restricted audit read resolve the legacy bypass. The faucet still has only `STAGING_FAUCET=1`; unlike chaos, its mount rule does not also require `OPINIONS_ENV=staging`, so it does not meet round 1's explicit non-production-mode requirement.

6. **PARTIAL — unwind lifecycle and non-negativity.** Excluding `Paid` from true unwind and making post-payout relief a house-funded credit correctly removes the impossible paid clawback. `Voided` is nevertheless already paid, and the proposed receivable path for spent/withdrawn proceeds has no valid ledger entry model and conflicts with D27; the E2E only proves exact restoration when no withdrawal occurred. See NEW-3.

7. **PARTIAL — unwind authority, lineage, and derived state.** A market-primary authority row, unique reversal lineage, and the enumerated seed/fee/dust/position/realization treatment address the main duplicate-reversal defects. The plan still leaves the atomicity boundary undecided as "one tx or a persisted-stage saga if oversized" without specifying saga stages, fencing, leases, crash recovery, or namespaced reversal ledger keys. Those choices are the exactly-once contract, not an implementation detail.

8. **PARTIAL — ledger-exact invariants.** D27 is a substantial correction: per-currency sum-zero/non-negativity/contra/payment/market/job checks and `collateral_at_close` are the right categories. D30 then adds a receivable class that identity 3 does not include, while saying elsewhere that identities include receivables; treating a non-cash claim as USDC also invalidates the cash meaning of the contra identity. See NEW-3.

9. **RESOLVED — one consistent invariant snapshot.** `InvariantReadTx`, one read-only repeatable-read Pg transaction, fake snapshot cloning, statement timeout, as-of marker, and the concurrent-commit contract directly satisfy the finding. Scheduling the expensive sweep outside the convoy is also appropriate.

10. **PARTIAL — replay determinism.** The plan honestly stops claiming byte-identical live executions and separates latency/outcomes from the deterministic artifact. It does not yet define a coherent executable artifact: dry-run has no `market_view`, while persona/ring decisions require one, and the trace omits the versioned scenario/RNG/state-transition contract needed to replay stateful rings and retries. See NEW-4.

11. **PARTIAL — deterministic mid-payout crash.** The named readiness barrier after payout ledger work and before commit is the right proof shape. No application fault port, injection point, production Noop boundary, or file owner is specified, while W4 owns only relay/WS adapter seams. Thus the promised point is not implementable from the inventory without an unplanned edit to the resolution/ledger path. See NEW-5.

12. **RESOLVED — chaos containment and deterministic fault contracts.** The two-factor staging arm, fail-fast parsing, health disclosure, Noop transparency, per-fault contracts, and per-connection seeded WS drops resolve the finding.

13. **UNRESOLVED — compiling, file-disjoint wave.** W1 and W2's newly named ops route/DTO/Pg files are textually disjoint and `chaos.rs` has one owner, but the complete work is not file-disjoint. Audit, receivables, config stamping, staging signup, crash-barrier injection, central registration, and test-double changes require numerous existing files absent from the ownership list. Task 6.0 is simultaneously too vague to freeze those contracts and too broad to complete safely as a pre-wave skeleton. See NEW-6.

14. **RESOLVED — simswarm architecture and gates.** D28 makes simswarm an outer crate with no internal dependencies, owns its wire DTOs, confines HTTP construction, injects process/sleep/network/time roles, adds both dependency-gate changes in 6.0, and adds the fourth 100% coverage recipe. These directly resolve the round-1 gate and coverage findings.

## New findings

### NEW-1 — BLOCKER — D24/D25 and exit criterion 4: the fence order turns an emergency pause into a convoy drain and holds the config singleton while draining

**Scenario:** At the 2,000-agent close spike, every `PlaceTrade` and `CastVote` obtains the global and market shared class-4 fences before blocking on the existing class-2 user lock or market row. All already-granted readers retain those fences through commit. A market/global pause requesting the exclusive fence must therefore wait for the entire downstream backlog to serialize, not merely the currently executing writer. Because `SetConfig` locks `config_generation` before acquiring the pause fence under D24's stated write path, unrelated config changes also block for that whole drain. CastVote makes this worse by holding trading fences even though trading pause is expressly not allowed to bind voting. This is not a class-1/2/3 deadlock as currently described, but it is an unbounded serialization/availability failure and defeats "instantly effective."

**Fix:** Give trading-global, trading-market, and voting-market distinct fence namespaces; only `PlaceTrade` takes trading fences and only `CastVote` takes the voting fence. Prevent requests queued on user/market locks from holding the shared pause fence: either acquire it immediately before the first authoritative write after downstream locks under a documented one-way lock graph (pause writers must never take those downstream locks), or specify a bounded admission/active-writer protocol with an epoch. A pause patch must acquire all applicable exclusive fences in canonical order before the generation row, then validate/write/commit. Add a 2,000-request convoy test that bounds pause latency and proves new writers abort while votes continue.

### NEW-2 — BLOCKER — D26/Task 6.0: `AuditWrite` cannot make the existing multi-transaction publication route atomic

**Scenario:** `PublishDraft::execute` durably commits Claim, Seed, GoLive, job enqueue, and finish across separate transactions and is used by both `/publish_now` and the automatic publisher. An audit row in any one `ContentTx` can precede or follow observable effects in other commits; a crash leaves either an audit without the advertised effect or an effect without its audit. The same shared `AdvanceMarket`/`ResolveMarket` use cases need to distinguish machine calls from authenticated admin calls. Merely adding a required trait method also forces coordinated edits to `InMemoryStore`, `PgTx`, `FakeContentTx`, `TestStore`, contracts, all constructors, and command types; an `Unavailable` placeholder either breaks Phase 0–5 suites/routes or leaves the effects unaudited.

**Fix:** Make `publish_now` atomically insert an idempotent publication command plus audit row, then let the existing leased/saga runner execute it, or define per-stage audits tied to one durable command authority and stop claiming one audit is atomic with the whole saga. Add a typed `AdminContext`/machine actor at every shared use-case boundary and assign every existing call site, fake, Pg impl, and contract file to Task 6.0 or a single wave owner. Preserve old non-admin behavior in the Phase 0–5 contract suites while proving each admin entry point's effect/command and audit are all-or-nothing.

### NEW-3 — BLOCKER — D27/D30 and migration 0008: the receivable account cannot satisfy the six identities as stated

**Scenario:** Suppose reversing X of a user's credited proceeds finds only B < X still in the user cash account. Replacing the missing debit with a receivable in the same USDC ledger either requires the receivable to be negative (violating "every non-external account >= 0") or a positive receivable plus a house leg that no longer represents the cash reversal without double-counting the house funding. Identity 3 omits receivables entirely, yet D30 says they are included. Even if algebraically forced into the internal sum, a non-cash claim is then counted as collateral against the External cash contra account.

**Fix:** Choose an accounting model before migration: preferably book the cash shortfall to house in the reversal transaction and record the user's debt in a separate non-cash receivables subledger/fact table, excluded from the cash contra identity; alternatively introduce a distinct receivable currency plus its explicit contra/equity accounts and identities. Specify exact legs for full balance, partial balance, zero balance, collection, and write-off, and run each through all six fake/Pg invariants. Update D13/D27 and the owner/currency schema consistently.

### NEW-4 — BLOCKER — D28 and exit criterion 2: dry-run schedule and trace replay do not define one implementable deterministic contract

**Scenario:** `--dry-run` has no network and therefore no `market_view`, but persona and ring decision functions take `market_view`; it cannot emit the same concrete "intent" object described by `(tick, agent, local_seq) -> intent` unless intent means only a decision opportunity. Stateful rings also depend on prior outcomes. The trace records per-intent view/action/outcome but does not pin a scenario manifest/config version, canonical encoding, decision-code/schema version, RNG derivation/counter consumption, same-tick ordering for a ring's vector actions, state transition timing, retry classification, or how a WS gap snapshot becomes the next recorded view. Two implementations can satisfy the prose and produce incompatible logs.

**Fix:** Define a versioned canonical run manifest and trace schema. Separate `PlannedOpportunity` (dry-run reproducible without views) from `DecidedAction`; define total ordering, logical IDs, per-agent/ring RNG streams and state updates, canonical JSON/bytes, view acquisition at each tick, HTTP/WS outcome normalization, gap/snapshot records, and deterministic retry scheduling. Replay must reconstruct ring/persona state solely from the manifest plus ordered trace and reject schema/config/code-version mismatches. Update the exit criterion to compare the artifact that dry-run can actually produce.

### NEW-5 — BLOCKER — D29/§2 W4: the payout crash point has no clean-architecture seam or owner

**Scenario:** The required point is after `ResolveMarket` calls `ledger_apply(Payout, ...)` and before its transaction commits. W4 owns `simswarm/src/chaos.rs`, `relay.rs`, and `ws.rs`, none of which can observe that in-transaction point. Implementing file touch/blocking directly in `resolve_market.rs` imports environment/filesystem/process concerns into application code; implementing it generically in `PgTx::ledger_apply` affects every ledger writer and is not owned by W4. A synchronous block can also stall a Tokio worker rather than provide a controlled async readiness handshake.

**Fix:** In Task 6.0 define and inject a narrow async `ResolutionCrashPoint` application port with a production `Noop`; place exactly one call after payout ledger insertion and before later resolution writes/commit. W4 owns a staging-only adapter that atomically publishes readiness and awaits cancellation/kill, and main composition selects it only under the two-factor arm. Name the application, adapter, main, fake, and contract files in the ownership map and prove Noop transparency.

### NEW-6 — BLOCKER — §2: the claimed file-disjoint inventory omits required shared and existing files

**Scenario:** The named W1–W4 files do not cover the implementation promised by the design. Receivables require at least `domain/src/ledger.rs`, `application/src/model.rs`, `adapters/src/pg/rows.rs`, and the shared ledger account implementation. Audit requires `advance_market.rs`, `resolve_market.rs`, `comments.rs`, several `content/*.rs` files, fake transactions, `moderation_escalate.rs`'s delegating `Store`, and HTTP contract tests. Live-immutable stamping/repricing reaches seed/publication/model/row code. The aged-signup override reaches create-user and existing routes. The crash point reaches resolution/ledger/main. The one RBAC table and subrouter/OpenAPI/module registration are central shared files needed by both W1 and W2. None has a wave owner, while Task 6.0 only says "stubs" and does not name an exhaustive per-file freeze surface.

**Fix:** Replace the directory-level inventory with an exhaustive file matrix covering ports, models/errors/events, all Store impls/test doubles, AppState/main, central route/module/OpenAPI registration, existing use cases, domain/row mappings, tests, and scripts. Prewrite final compiling interfaces plus behavior-tested fake/Pg unavailable factories in 6.0, then explicitly transfer each non-frozen implementation file to one worker. Split 6.0 into reviewable preparatory tasks; run the full Phase 0–5 suites and skeleton gates before freezing. Any later shared-file need must stop all waves as the plan says.

### NEW-7 — BLOCKER — D24/D26: sensitive two-phase config changes have no durable proposal authority

**Scenario:** Finance proposes a fee/seed/integrity patch, another config patch advances the singleton generation, and superadmin later confirms. The schema lists `config_entries`, `config_generation`, and audit rows but no proposal row carrying the patch, base generation, proposer, expiry, idempotency key, or status. `admin_actions` is evidence, not mutable command authority. Confirmation therefore cannot know what immutable proposal it is approving, prevent replay/double confirmation, or decide whether to reject/rebase and revalidate a stale prospective snapshot.

**Fix:** Add a `config_change_proposals` authority keyed by a namespaced idempotency key and immutable patch hash, with base generation, proposer principal/role, expiry, status, confirmer, and resulting generation. Proposal and confirmation each audit atomically; confirmation locks the proposal and all needed pause fences in canonical order, then the generation row, revalidates the complete current prospective snapshot, and either applies once or returns typed stale/conflict. Add concurrent propose/confirm/replay/expiry and intervening-generation Pg contracts.

### NEW-8 — BLOCKER — D25a/exit criterion 3: fee preview semantics contradict the persisted pool authority and lack change history

**Scenario:** D25a says a fee config change applies only to new markets' pool rows and a live pool changes only through audited `reprice-market`. Exit criterion 3 nevertheless requires a new preview after the config change to quote the new fee while also asserting the live market's pool fee is unchanged, then requires the old preview to fail as stale. Both previews cannot be authoritative for the same live pool. Separately, `config_entries` has no `changed_generation`; after any generation mismatch, `PlaceTrade` cannot determine whether a `next-trade` key changed "in between" without history.

**Fix:** Choose one policy. If fee is new-market-only, existing-market previews remain unchanged and fee-only config drift must not stale them; test the new fee on a market created after confirmation. If live repricing is intended, make `reprice-market` atomically update the pool's fee/version and audit it, and have preview/place compare that pool version. Add `changed_generation` or an immutable generation-change log for every key whose selective staleness is required, and state the exact read/lock order.
